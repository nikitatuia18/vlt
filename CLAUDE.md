## Правила
- **Сначала дизайн-система.** Перед любым элементом (кнопка, иконка, текст, цвет, отступ) смотри `docs/ui-kit.md`, `/ui-kit` и токены; не рисуй «на глаз». Нужного нет — предложи добавить в UI Kit, а не лепи локальный вариант.
- **Анимации появления, стекло, свечение, тема-сцены тоже берутся из UI Kit** (`docs/ui-kit.md`, разделы 7–9; `src/motion/reveal.tsx`): сначала готовая заготовка, новую вводим через UI Kit (вариант в `reveal.tsx`, плитка в `/ui-kit`, строка в таблице 7.1).
- **Весь текст сайта появляется по словам** (`RevealLines`: слова выезжают из масок одно за другим, `docs/ui-kit.md` 7.0). Подписи кнопок и бейджей это уже делают сами (`ButtonLink`, `Badge`, `labelReveal`). Исключения только цифры (`CountUp`), карточки на глобусе, значки баннера, меню узких экранов и тексты внутри иллюстраций карточек Features (они часть анимаций дизайнера со своим таймлайном). Тест `every text of the page appears word by word` называет любой текст в обход правила.
- **Новые авторские эффекты** (смена темы, переходы, необычные анимации) сначала показываем вариантами на тестовой странице, на сайт подключаем после выбора дизайнера: по описанию словами вид не угадать (шторка не понравилась, пришлось переделывать).
- **Тяжёлые эффекты** (`backdrop-filter`, особенно с `url()`, большие `blur`, canvas-карты в движущихся блоках) не добавляем без замера: Playwright + CDP `Emulation.setCPUThrottlingRate` ×4, долгие задачи (`longtask`), задержка текста; причины и приёмы — `docs/lessons.md`.
- Никаких хардкод-цветов, размеров, шрифтов — только токены из `tokens.css` / `typography.css`. Значение пользователя без токена (например, цвет из прототипа): если есть близкий токен — **выбираю его сам, без вопроса**, и сообщаю одной строкой («взял X вместо Y, потому что…»); вопрос только если ничего подходящего нет. Тогда — одно исключение с пометкой в `tokens.css`, строка в `docs/tokens-map.md` (раздел «Не из Figma») и предложение завести переменную в Figma.
- Код пользователя (прототипы) переносим в проект с адаптацией под стек и дизайн-систему, сохраняя его параметры и поведение; что изменили — записываем в `docs/blocks/<block>.md`.
- Слои в Figma не переименовываем без утверждённой карты; перед массовым переименованием — бэкап страницы.
- Блок: сначала статика и сверка, потом анимация.
- UI Kit: перед новым компонентом смотри `docs/ui-kit.md` и витрину `/ui-kit`; общий элемент (встретился во втором блоке) выносится в `src/components/ui/`, добавляется в витрину и в `docs/ui-kit.md`.
- Тесты блока (`tests/<block>.spec.ts`): скриншоты на 393 / 768 / 1024 / 1280 / 1440 / 2560, размеры из макета, нет горизонтального скролла, Dark. Скриншоты смотреть глазами, а не только по зелёным тестам.
- Адаптив: mobile-first, один компонент на блок на всех вьюпортах (десктоп, планшет, мобильный); правила — `docs/responsive.md`.
- Код читаем сторонним программистом: понятные имена, комментарии только про «почему», структура и имена по `docs/naming-spec.md`.
- Анимации: motion.dev; общие easing/duration — в `src/motion/tokens.ts` (простые переходы цвета и фона допустимы через CSS `transition`, как hover); всегда учитывать `prefers-reduced-motion`.
- Имя слоя → имя компонента/класса по `docs/naming-spec.md`; не придумывать свои имена.
- Спек анимации (`docs/blocks/<block>.motion.md`) подтверждает пользователь до написания кода.

## Самообучение (обдуманно, не всё подряд)
Цель: чтобы одна и та же ошибка или договорённость не повторялась. Перед записью проверь все четыре условия:
1. **Неочевидно** — этого нет в коде, макете и `git`-истории и не следует из текущих правил.
2. **Повторится** — будет полезно в других блоках/сессиях, а не только в этой правке.
3. **Проверено** — подтверждено пользователем или результатом (сборка, сверка), а не моя догадка.
4. **Коротко** — формулируется в 1–3 строки с причиной.

Не записываем: разовые правки значений, ход обсуждения, то, что уже написано в скиллах, временные хаки.

Куда писать:
| Что | Куда |
|---|---|
| Договорённость или предпочтение пользователя («так делаем всегда») | правило в этом файле, раздел «Правила» |
| Уточнение процедуры конкретного этапа (анимация, токены, сборка блока) | соответствующий `SKILL.md` |
| Ошибка/ловушка и как её обойти (Figma MCP, Tailwind, motion) | `docs/lessons.md` |
| Параметры конкретного блока (тайминги, решения) | `docs/blocks/<block>.md` / `<block>.motion.md` |

Порядок: когда замечаю кандидата, в конце ответа предлагаю одной строкой «Записать: <суть> → <куда>?». Пишу после «да». Исключение — мелкая запись в `docs/lessons.md` о ловушке, которая только что стоила нам времени: её добавляю сам и сообщаю об этом. Правила в `CLAUDE.md` и скиллах меняю только с согласия.
Если новая запись противоречит старой — переписываю старую, не добавляю рядом. Раз в несколько блоков (по просьбе пользователя) пересматриваем `docs/lessons.md` и удаляем устаревшее.
